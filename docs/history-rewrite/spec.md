# EndlessCode 历史时间线整理 Spec

## 背景

当前本地 `main` 的开发成果主要以 PR 合并结果呈现，部分 PR 将功能实现、测试补齐、文档更新和发布准备合并在同一个较大的提交或合并节点中。GitHub PR、PR 内部提交、提交日期和文件变更记录能够证明这些工作曾分阶段完成，但主线阅读时阶段边界不够清晰。

本次工作只整理本地 `main`，不修改 GitHub 远程分支。操作前已创建 Git 全引用备份和工作区快照。

## 目标

- 将有明确证据支持的阶段拆成连续、可读的本地提交。
- 让提交信息能区分功能、修复、测试、文档、示例和发布/工程整理。
- 保留历史事实：提交顺序依据 PR、原始提交顺序和文件变更证据，不虚构不存在的功能；仅重新分布提交日期。
- 保持整理后 `main` 的最终文件树与整理前一致。
- 保留当前工作区中的未跟踪文件，不把它们纳入历史整理。

## 功能需求

- F1: 以当前本地 `main` 为唯一改写对象，保留 `dev`、`test` 等其他本地分支不变。
- F2: 在改写前保留可恢复的仓库备份，包括全部 Git 引用和工作区快照。
- F3: 根据 PR、PR 内部提交、提交日期和文件变更，将可验证的阶段拆为独立提交。
- F4: 优先形成以下类型的里程碑：核心功能、修复/健壮性、测试覆盖、文档/示例、CI/发布整理。
- F5: 在保持提交顺序和阶段边界不变的前提下，将提交作者时间和提交者时间重新分布到 2026-03-01 至 2026-08-19；阶段之间保留 1-10 天的自然间隔，最后一个提交落在 2026-08-19。
- F6: 整理后的 `main` 采用线性提交历史，不保留原 PR merge commit 作为主线结构节点。
- F7: 整理完成后，最终树内容、分支指向关系和未跟踪工作区文件均可验证。

## 非功能需求

- N1: 任何改写操作都必须可通过备份恢复。
- N2: 不执行远程 push、force push、删除远程分支或修改 GitHub 数据。
- N3: 不修改与本次历史整理无关的源代码行为。
- N4: 每个新提交应有单一、可解释的主题，提交信息使用清晰的中英文混合项目惯例；新时间不得改变提交顺序。
- N5: 整理后运行项目现有测试、格式检查和差异检查，失败时停止并修复。

## 不做的事

- 不整理 `dev`、`test` 或其他非 `main` 分支。
- 不把 `.coverage`、`closure_demo.py` 或其他当前未跟踪文件加入提交。
- 不凭空补造 Issue、PR、测试结果或功能阶段；日期分布是时间线展示调整，不代表新增开发事实。
- 不改变最终代码、文档和配置的内容，只改变提交边界、提交信息和本地提交元数据。
- 不向 GitHub 推送改写后的历史。

## 验收标准

- AC1: `main` 的最终树与改写前 `main` 的最终树一致；验证：比较备份引用与新 `HEAD` 的文件清单和内容哈希。
- AC2: `main` 形成连续线性历史，且不再以原 PR merge commit 作为主线节点；验证：运行 `git log --first-parent --merges` 和提交拓扑检查。
- AC3: 每个新增提交都能关联到至少一项 PR、原始提交、文件变更或测试记录；验证：查看整理映射表与 `git show --stat`。
- AC3a: 新提交作者时间和提交者时间均位于 2026-03-01 00:00:00 +0800 至 2026-08-19 23:59:59 +0800，时间单调递增，最后一个提交日期为 2026-08-19；验证：运行 `git log --reverse --date=iso` 检查全部提交。
- AC4: 历史中至少包含功能、测试、文档/示例和工程/发布类可读里程碑；验证：按提交主题检索并逐项核对文件范围。
- AC5: `dev`、`test` 分支指向保持不变；验证：比较改写前备份中的分支哈希与当前分支哈希。
- AC6: `.coverage`、`closure_demo.py` 仍保持未跟踪且内容不变；验证：运行 `git status --short` 并比较文件哈希。
- AC7: 项目测试和工程检查通过；验证：运行现有 pytest、ruff 和 compileall 命令并记录结果。
- AC8: 备份可用于恢复原始仓库；验证：使用 `git bundle verify` 检查备份包。
